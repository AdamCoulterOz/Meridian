Meridian

Language-aware structural merge tooling for source formats that Git can only see as text.

.NET 11 Apache-2.0 XML · JSON · JSON5 · YAML · HTML Git merge & diff driver
View on GitHub How it works Quick start

What it is

Meridian is for repositories where normal line-based merging is too fragile: unpacked solution XML, JSON config, YAML manifests, generated-ish metadata, templated files, and nested formats such as JSON inside XML.

Instead of asking Git to guess from lines, Meridian parses each side of a three-way merge into a document tree, matches nodes by schema-defined identity, merges the structure, and writes normal Git conflict markers only where the structural merge cannot be resolved safely. It is domain-neutral: repositories teach it their formats through schema files rather than baking product knowledge into the tool.

The problem

A plain text merge turns two independent, non-competing edits into a conflict:

<<<<<<< ours
<label description="Near Miss" languagecode="1033" />
<label description="Incident"  languagecode="3081" />
||||||| base
<label description="Near Miss" languagecode="1033" />
<label description="Near Miss" languagecode="3081" />
=======
<label description="Safety Event" languagecode="1033" />
<label description="Near Miss"    languagecode="3081" />
>>>>>>> theirs

Those edits are not really competing — each side changed a different label. With a schema that says languagecode identifies sibling labels, Meridian merges the structure instead and produces the obvious result: 

<label description="Safety Event" languagecode="1033" />
<label description="Incident"     languagecode="3081" />

Sorting siblings would also dodge this one case, but many structured files mix unordered lookup collections with ordered UI layout, execution steps, and fallback precedence — sorting everything corrupts those. Meridian keeps order meaningful only where the schema says it is.

How it works

  1. Parse. A format adapter turns each of base, ours, and theirs into a document tree of nodes (kind, fields, value, children).
  2. Identify. Schema rules assign each node a stable identity that is local to its parent — a discriminator attribute, an element value, a composite key, or an explicit ordered slot.
  3. Merge structurally. Nodes are matched by identity, not by line position. Independent edits to different nodes both apply.
  4. Respect order only where it matters. Sibling order participates in the merge only for parent paths the schema lists as orderedChildren.
  5. Fail loud, never guess. If repeated siblings cannot be given unique identities, or both sides change an ordered collection differently, Meridian emits a conflict instead of silently aligning the wrong nodes.
base source   ─▶ adapter ─▶ base tree   ┐
ours source   ─▶ adapter ─▶ ours tree   ├─▶ identity assignment
theirs source ─▶ adapter ─▶ theirs tree ┘   ─▶ three-way structural merge
                                            ─▶ adapter render (markers only where needed)

Core concepts

Identity is local

Identity means "inside this parent, siblings with this node name are matched by this value" — not global uniqueness. Ambiguous identity is an error, not a guess.

Order is opt-in

Once nodes have identities, sibling order is ignored by default. Declare orderedChildren only where sequence is genuinely semantic.

Nested content

A scalar that contains another format — JSON inside XML, HTML inside JSON — can be parsed, merged as its own tree, and re-embedded with correct escaping.

Schema-owned semantics

Discriminators, ordered children, content formats, companion files, and format aliases live in *.meridian.yaml — composable, discoverable, and consumer-owned.

Quick start

Build from source (requires the .NET 11 SDK) and run a structural three-way merge:

git clone https://github.com/AdamCoulterOz/Meridian.git
cd Meridian
dotnet build Meridian.slnx
dotnet test Meridian.slnx

dotnet run --project source/Tools/GitMerge/GitMerge.csproj -- \
  merge-file --base base.xml --ours ours.xml --theirs theirs.xml --path catalog.xml

Wire it into a repository as a Git merge driver, then opt files in with .gitattributes:

# .git/config (or repo config)
[merge "meridian"]
    name = Meridian structural merge
    driver = dotnet run --project ../Meridian/source/Tools/GitMerge/GitMerge.csproj -- \
             merge-file --base %O --ours %A --theirs %B --path %P

# .gitattributes
*.xml  merge=meridian diff=meridian
*.json merge=meridian diff=meridian
*.yaml merge=meridian diff=meridian

A minimal schema describes only merge-relevant facts:

schemaVersion: 0.1
name: catalog

defaults:
  globalDiscriminatorFields: [id, Id, languagecode]

files:
  - match: catalog.xml
    discriminators:
      - path: Catalog/Products/Product
        key: { attribute: sku }
    orderedChildren:
      - Catalog/DisplayOrder

Full documentation, schema reference, and library usage live in the project README and architecture notes.
